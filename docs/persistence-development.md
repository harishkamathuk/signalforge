# PostgreSQL persistence development

M6 uses native PostgreSQL in WSL for primary local development. Docker is not required.
GitHub CI uses a fresh PostgreSQL 16 service to validate migrations and integration tests.

## Local prerequisites

- Python 3.12
- PostgreSQL 16 (or the project-supported PostgreSQL major version)
- a local database/user dedicated to SignalForge development

Example PostgreSQL setup from `psql` as an administrative user:

```sql
CREATE USER signalforge WITH PASSWORD 'choose-a-local-password';
CREATE DATABASE signalforge OWNER signalforge;
```

Export a SQLAlchemy/psycopg connection URL. `.env.example` documents the expected format;
SignalForge does not automatically load `.env` files.

```bash
export DATABASE_URL='postgresql+psycopg://signalforge:...@localhost:5432/signalforge'
```

## Schema lifecycle

Alembic is the authoritative schema-management mechanism. Application startup must not
silently create or mutate the schema.

Apply all migrations:

```bash
alembic upgrade head
```

Inspect the current revision:

```bash
alembic current
```

Create a candidate migration after changing persistence metadata:

```bash
alembic revision --autogenerate -m 'describe schema change'
```

Autogenerated migrations are only a starting point. Review the complete upgrade and downgrade
operations, constraints, Decimal precision, timestamp semantics and deterministic identity keys
before committing them.

## Architecture boundary

SQLAlchemy records under `signalforge.persistence` are persistence models, not SignalForge domain
objects. Domain/runtime code must not depend on ORM entities or SQLAlchemy sessions directly.
Repository, Data Mapper and Unit of Work behavior is introduced by later M6 issues.

The initial schema implements ADR-003's hybrid model:

- immutable provenance and runtime facts are retained for audit/reproducibility;
- mutable authoritative setup/trade/position and checkpoint state is represented separately;
- no event store or broker/OpenAlgo-specific schema is introduced.

## CI

CI starts a clean PostgreSQL service, runs `alembic upgrade head`, then runs the normal test suite.
Migration integration tests also verify that the initial revision can downgrade to `base` and
re-upgrade to `head` reproducibly.
